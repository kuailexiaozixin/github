# 运维判据的来历（ops 参考）

本篇只回答 `github-ops/SKILL.md` 里那些阈值与取舍"为什么是这个数、不这样会怎样"。命令、参数与出口判据以 SKILL 主线为准，本篇不含命令流程。

## 标签体系为什么要先建再分诊

分诊时逐条临时造标签，同一个含义会长成 `bug`、`Bug`、`type:bug` 三种名字，之后的批量查询与统计就查不全。先约定类型与优先级两组标签，分诊只做"贴哪个"，判断空间收窄成可枚举，两个人分诊结果才会一致。类型维度取 bug、feature-request、question、documentation、enhancement、duplicate、invalid、good-first-issue；优先级取 critical（破坏性或安全）、high（影响面大）、medium（可有可无）、low（外观）。

分诊动作固定为读正文、查重、贴标签、回复、补复现信息五步，顺序不能倒：没查重就贴标签，重复的 issue 会被当成两个独立缺陷各修一遍。

## 为什么活跃度的三条线是 14 天、7 天、30 天

三条线量的不是同一件事，所以数值不同。

issue 满 14 天无人回，报告人多半已经自己找了别的方案，此时打 `stale` 并问一次，是为了给"还活着"的项一次留名机会；这条线再短就会误伤低频但真实的缺陷。

PR 满 7 天无人看，作者还在等，社区贡献者会直接放弃。7 天是一个工作日周期的上限，超过它，PR 的上下文对作者和审查人都已经凉了。

issue 打 `stale` 后 30 天仍无回应才关闭，是因为关闭要留证据：报告人已经不在，继续挂着只会让队列失真。三条线叠起来的效果是"没人管的问题不会永久堆积，但每一步都有反悔窗口"。

## 为什么合并默认用 squash

长期分支上常有"改回上一版""调试日志"这类提交。merge 保留全部提交，主干历史里就混进与功能无关的过程记录；rebase 保留过程且改写历史，对已共享的分支会造成他人本地与远端不一致。squash 把一条 PR 压成一次提交，主干上一次提交对应一个可解释的功能变化，回滚也只需回滚一条。代价是丢失分支内部的历史，因此审查时要求 commit message 足以解释整条 PR，而不指望细粒度提交。

## 为什么 release 前置是"主干 CI 全绿"

release 是给外人用的产物，一旦发出就可能被缓存、被依赖。发一个主干测试未过的版本，之后只能发新版覆盖并在 changelog 里解释，声誉成本比延迟几小时高。所以发布顺序被固定成：主干全绿、审过未发布改动、生成 changelog、建 release、传资产、验证，任何一步不满足就停在这一步，而不是先建后补。

## 为什么安全告警要每周一次且高危当天处理

依赖漏洞的公开到利用之间有窗口期，仓库是公开的话攻击者可以扫 Dependabot 告警直接读到受影响版本。当天处理高危不是为了修好，是为了先决定"要不要临时下线、要不要发公告"。secret scanning 的告警不能只在 GitHub 上标已解决，密钥仍在提交历史里，必须先在服务侧吊销再改历史。

## 为什么质量门禁是"五项不满足不算收口"

门禁的五条各自对应一种"看起来完成实则没完成"的失效：issue 有标签但没人负责，等于下周还要重分诊；PR 未回，作者已流失；CI 只重跑未定位，同一失败还会再来；release 资产与 changelog 不符，用户拿到错文件；告警无人跟，等于没看。任何一条没满足，本轮维护的效果就不可验证，所以不允许宣布结束。
